# Building a Free Safari Tab Reload Extension with AI Assistance

> This is a curated historical development story, not a complete session export or a substitute for the project's current installation instructions. Published after the author's review.

## Why build it?

The goal was straightforward: create a macOS Safari extension that lets a user choose an interval for automatically reloading an open tab.

The author's motivation was to provide a **free, open-source option**, with code that people can inspect, modify, and build themselves.

An AI coding assistant helped implement the extension, interpret errors, and prepare its distribution. The author ran commands, reviewed results, tested the app in Safari, and made decisions about publication.

## The workflow

This was an iterative, tool-assisted conversation:

1. Describe a desired feature.
2. Have the assistant propose a file change or command.
3. Run the action locally and return its output.
4. Inspect the result and adjust the next step.
5. Test in the actual browser rather than relying solely on generated code.

The assistant did not independently verify every instruction before giving it. Some guidance needed correction when tested against the installed tools. Those corrections are part of the story, not something to hide.

## Implementing the extension

The initial implementation separated the project into:

- A Manifest V3 extension manifest.
- A background event page using Safari's alarms API.
- A toolbar popup with HTML, CSS, and JavaScript.
- Dependency-free Node.js tests with mocked browser APIs.
- A containing macOS app generated by Xcode's Safari extension converter.

The extension manages independent timers for each tab. The popup supports starting, updating, and stopping a timer. An ON badge indicates an active timer.

Intervals range from 60 seconds to 24 hours. The implementation restricts reloads to HTTP and HTTPS pages, skips pages already loading, and clears timers when tabs close or Safari restarts.

A recurring design constraint was that reloading can discard unsaved work. The interface warns about this, and the documentation explains that alarms may be delayed during sleep or by browser scheduling.

## Automated checks helped, but were not enough

Eight mocked background tests covered:

- Starting, reporting, updating, and stopping timers.
- Rejecting invalid intervals and unsupported pages.
- Reloading idle pages and ignoring unrelated alarms.
- Cleaning up closed or missing tabs.
- Transferring timers when tabs are replaced.
- Clearing stale timers on browser startup.
- Rejecting messages from unexpected senders.

JavaScript syntax checks and manifest/resource checks also passed.

These checks validated the modeled behavior, not the complete Safari runtime. Actual installation and browser testing remained necessary.

## Getting Xcode ready

The first packaging obstacle was that Apple's Command Line Tools did not include the Safari Web Extension converter. Full Xcode had to be installed and selected.

Two mistyped command paths caused additional errors. Reading the literal command, rather than assuming a deeper system problem, resolved those.

After installation, the converter failed because Xcode's first-launch components were incomplete. Running Xcode's first-launch setup installed the missing components, after which project generation succeeded.

**Lesson:** distinguish a missing tool, a typo, and incomplete tool setup before changing application code.

## Converter warnings and local Safari testing

Project generation produced warnings about an unsupported `persistent` manifest key and missing icons. These did not prevent generating or building the project.

The unsupported setting was documented as a warning observed during development, not treated as evidence that all Manifest V3 behavior was compatible. The icons were addressed in a later iteration.

The initial app built successfully but its extension did not appear in Safari until the local unsigned-extension setting was enabled. Restarting Safari resets that setting, which made the order of setup steps important.

The author then reported that the extension worked in Safari.

**Lesson:** a successful native build is not the same as a registered, enabled, functioning browser extension.

## Adding icons

The author supplied square artwork. The assistant generated PNG variants for the extension, updated the manifest, and added the resources to the existing Xcode extension target.

A follow-up changed the containing app's Dock and Finder icon by populating the macOS app icon asset catalog, including its high-resolution variant.

Build checks confirmed that the extension icons and compiled app icon were present in the app bundle. This was more useful than checking only that the source images existed.

## Choosing a free distribution route

The author wanted Homebrew installation without paying for an Apple developer subscription.

The selected route was a public source repository, an ad-hoc-signed app ZIP hosted as a GitHub Release, and a Homebrew cask in the same repository.

Ad-hoc signing does not establish a verified developer identity and is not notarization. Homebrew does not bypass Gatekeeper or Safari's unsigned-extension restrictions. Users still need to approve the app as appropriate and enable unsigned extensions in Safari.

The repository used the MIT license. This story records that choice without evaluating its legal effect or promising protection from liability.

## Source publication was not the end of distribution

Creating a source repository did not automatically make it installable with Homebrew. A separate release artifact and cask definition were required.

The published ZIP was downloaded and inspected. The checks established that the particular release contained an Apple Silicon binary and required macOS 27.2 or newer. These are properties of that release, not a promise about other architectures or older systems.

The cask specified a versioned download URL, a SHA-256 checksum, the app artifact, and platform requirements.

Several validation steps exposed problems:

- Homebrew required the cask to be loaded from a tap rather than an arbitrary source path.
- The installed Homebrew version required explicit trust for a third-party cask.
- A minor-version macOS dependency string was rejected by Homebrew.
- The dependency was changed to the supported major-version symbol, with a caveat preserving the actual app requirement of macOS 27.2 or newer.

Cask style, audit, and download validation then passed. This did not itself prove that the app would appear in Safari on a clean installation.

## Testing the downloaded app in a virtual machine

The author installed the app through Homebrew in a macOS virtual machine and enabled unsigned extensions, but initially could not find the extension in Safari.

The missing step was launching the containing app inside the virtual machine. Homebrew installed the app but did not launch it.

After opening the containing app and proceeding to Safari's Extensions settings, the author reported that the problem was resolved. The README was updated to make first launch explicit and to distinguish the Developer setting from the individual extension's enablement checkbox.

**Lesson:** test the installation path that other people will use, ideally in a clean environment. A development machine can hide registration or setup requirements.

## Updating users through Homebrew

Homebrew upgrades follow the version recorded in the cask. A new source commit or GitHub Release alone does not update installations.

Each release needs:

1. A tested app build and packaged artifact.
2. A versioned GitHub Release download.
3. An updated cask version and checksum.
4. Any revised platform requirements and user instructions.

This keeps downloads reproducible and checksum-verified instead of relying on an unchecked moving latest URL.

## What this example demonstrates

AI assistance was useful for scaffolding a small application, writing tests, navigating packaging tools, and iteratively documenting discoveries.

Human involvement remained essential for:

- Choosing the project's purpose and distribution constraints.
- Reviewing changes and deciding what to publish.
- Running privileged or interactive setup commands.
- Testing the actual Safari experience.
- Identifying gaps between plausible instructions and working installation steps.

The most valuable output was not merely generated code. It was a progressively verified combination of code, tests, packaging, and documentation.
